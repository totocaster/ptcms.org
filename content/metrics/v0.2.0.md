Plaintext Metrics is a plain-text format for numbers recorded over time, such as room temperature, pages read, or the distance of a run. A file holds one fact per line. A person can read it in any editor, a program can parse it, and an agent can extend it.

This is a working draft. Section 12 lists what is still undecided.

## Overview {#section-1}

A metrics file is a list of lines. Each line is one JSON object, and each line is one of four things:

- a **header**, which names the format and whose definitions these are;
- a **definition**, which says what a metric means;
- a **record**, which states one number at one time;
- an **event**, which gathers the records of one occasion, such as a run.

A complete, valid file:

```jsonl
{"format":"plaintext-metrics/0.2.0","set":"ada/journal","by":"Ada"}
{"define":"room.temperature","v":1,"kind":"quantity","unit":"Cel","name":"Room temperature","combine":"mean"}
{"define":"reading.pages","v":1,"kind":"count","name":"Pages read"}
{"at":"2026-11-26T08:10+01:00","metric":"room.temperature","v":1,"value":19.5}
{"date":"2026-11-26","metric":"reading.pages","v":1,"value":42}
```

Three properties hold the format together:

- **Every record names its definition version.** The meaning of a number never depends on where its line sits in the file.
- **Lines are an unordered set.** Appending is the normal way to write, and sorting, merging and splitting are safe.
- **A file carries the definitions its records cite.** It stays readable on its own, without a second file or an application's settings.

### Conventions {#section-1.1}

The words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY mark the rules of the format. Each rule has an identifier in square brackets, such as [[M-5](#M-5)], which never changes and is never reused. "Writer" means any tool or person that changes a file. "Reader" means any tool that interprets one.

## Goals {#section-2}

- **Readable anywhere.** A file opens in any text editor and is useful with `grep`, `tail` and `jq` alone.
- **Durable.** A file still makes sense in ten years, without the software that wrote it.
- **Small.** A person or an agent can write a correct line without special tools.
- **Exact.** Two programs read the same file the same way.
- **Local.** Whoever keeps the data defines the metrics. No registry or central authority is required.

The format leaves three things out:

- **High-frequency streams.** Heart rate per second or a dense GPS track is usually better kept in its own file, with the summary numbers here.
- **Text as a value.** A value is always a number. Words go in labels and notes.
- **Queries and charts.** Those belong to tools built on the files.

## Files {#section-3}

A metrics file is one self-contained file. There is no second file for definitions.

> **M-1 · MUST · files** A metrics file MUST use the extension `.metrics`, as in `journal.metrics`.

> **M-2 · MUST · files** A file MUST be encoded as UTF-8 without a byte order mark.

> **M-3 · MUST · writers** A writer MUST end every line, including the last, with a line feed.

> **M-4 · MUST · readers** A reader MUST accept lines that end with a carriage return and a line feed.

> **M-5 · MUST · files** Each non-empty line MUST be exactly one JSON object written on a single line.

> **M-6 · MUST · readers** A reader MUST ignore blank lines.

> **M-7 · MUST NOT · files** A file MUST NOT contain comments or any other text that is not a JSON object.

> **M-8 · MUST NOT · readers** A reader MUST NOT give any meaning to the order of lines.

> **M-9 · MUST · readers** A reader MUST treat a line that appears more than once as a single line.

> **M-10 · MUST · files** A file MUST contain every definition that its records and events cite.

> **M-11 · MAY · files** A file MAY hold a header and definitions with no records. Such a file is a catalog that other files copy from.

> **M-12 · MUST · files** When the same definition appears in several files of one set, every copy MUST be identical.

A folder may hold any number of files. File names and the boundaries between files carry no meaning.

### Compressed copies {#section-3.1}

The working file is plain text.

> **M-13 · MAY · writers** A writer MAY produce a compressed copy, such as `journal.metrics.gz`, for sending or archiving.

> **M-14 · MUST NOT · readers** A reader MUST NOT require a compressed copy.

A compressed copy is a wrapper, not a second format.

## Lines {#section-4}

A line is recognised by which one of four fields it has.

| Line | Has the field | What it says |
|---|---|---|
| Header | `format` | Which format this file is, and whose definitions it uses. |
| Definition | `define` | What one metric, or one type of event, means in one version. |
| Record | `metric` | One number, for one metric, at one time. |
| Event | `event` | One occasion that several records belong to. |

> **M-15 · MUST · files** Every line MUST have exactly one of the fields `format`, `define`, `metric` and `event`.

Records and events cite a definition by name and version. A record may belong to an event, and an event may be part of a larger one. Nothing refers to a line by its position.

## Header line {#section-5}

```jsonl
{"format":"plaintext-metrics/0.2.0","set":"ada/journal","by":"Ada"}
```

| Field | Required | Meaning |
|---|---|---|
| `format` | yes | The format name, then the version of this specification that the file follows. |
| `set` | yes | The name of the definition set this file uses. |
| `by` | no | Who wrote the definitions: a person, a group or an organisation. |

> **M-16 · MUST · files** A file MUST have exactly one header line.

> **M-17 · SHOULD · writers** A writer SHOULD put the header on the first line.

> **M-18 · MUST NOT · readers** A reader MUST NOT depend on where the header is.

> **M-19 · MUST · files** The header MUST carry `format` and `set`.

> **M-20 · MUST · files** The value of `format` MUST be `plaintext-metrics/` followed by the version of this specification that the file follows, such as `plaintext-metrics/0.2.0`.

> **M-21 · MAY · files** The header MAY carry `by`.

The header holds nothing about how to view the data. When a day or a week begins is a choice each tool makes, not a fact about the file.

### Versions of the format {#section-5.1}

This specification is versioned with three numbers, as the rest of Plaintext Commons is.

- **Major.** Changes when a change breaks existing files or tools.
- **Minor.** Adds to the current major version without breaking it.
- **Patch.** Fixes mistakes.

### Sets {#section-5.2}

A set is one author's vocabulary: the definitions written by one person, group or organisation. There is no central authority, so the set name is what keeps two authors' definitions apart.

> **M-22 · SHOULD · writers** A set name SHOULD take the form `owner/name`, such as `ada/journal` or `clinic/trial-7`.

> **M-23 · MUST · files** Every line in a file MUST belong to the set its header names. A file holds one set.

Within a set, a name and version mean one thing in every file. Across sets, the same name may mean something different. Combining files from two sets is a tool's job.

## Definition lines {#section-6}

A definition line says what one metric, or one type of event, means. Definitions are written by whoever keeps the data, and each carries its own version.

```jsonl
{"define":"room.temperature","v":1,"kind":"quantity","unit":"Cel","name":"Room temperature","combine":"mean"}
```

### Fields {#section-6.1}

| Field | Required | Meaning |
|---|---|---|
| `define` | yes | The name of the metric or event type. |
| `v` | yes | The version of this definition. |
| `kind` | yes | How to read the number: `quantity`, `count`, `score`, `flag` or `event`. |
| `unit` | for a quantity | The unit of the value, or a list of compatible units. |
| `min`, `max` | for a score | The lowest and highest value. |
| `name` | no | The name to show people. |
| `about` | no | A plain description of what it measures and how to record it. Agents read this before they write. |
| `combine` | for a quantity | How several values in one period become one number. |
| `labels` | no | The labels its lines may carry, with their allowed values. |
| `levels` | no | For a score, names for its values, such as `{"1":"poor","5":"excellent"}`. |
| `metrics` | no | For an event, the metrics normally recorded in it. |
| `parts` | no | For an event, the event types that may be parts of it. |
| `was` | no | Earlier names of the same metric. |

> **M-24 · MUST · files** A definition MUST carry `define`, `v` and `kind`.

> **M-25 · MUST · files** A name MUST be lowercase words separated by dots, such as `room.temperature`. A word starts with a letter and may contain letters, digits and underscores.

> **M-26 · MUST · files** `v` MUST be a whole number, 1 or higher, counted separately for each name.

> **M-27 · MUST · files** `kind` MUST be one of `quantity`, `count`, `score`, `flag` and `event`.

### Versions {#section-6.2}

> **M-28 · MUST NOT · writers** A writer MUST NOT change a definition once any line cites it.

> **M-29 · MUST · writers** A writer MUST publish any change to a definition, even to its name, as a new definition line with a higher version.

> **M-30 · MUST · readers** A reader MUST interpret each value with the definition version its line cites.

> **M-31 · SHOULD · readers** When a view spans several versions of one metric, a reader SHOULD present it under the newest version's name.

A new version of one metric does not renumber any other.

```jsonl
{"format":"plaintext-metrics/0.2.0","set":"ada/journal"}
{"define":"book.rating","v":1,"kind":"score","min":1,"max":5,"name":"Book rating"}
{"define":"book.rating","v":2,"kind":"score","min":1,"max":10,"name":"Book rating","about":"How much the book was worth reading, rated when finished."}
{"date":"2026-03-01","metric":"book.rating","v":1,"value":4}
{"date":"2026-03-09","metric":"book.rating","v":1,"value":3}
{"date":"2026-07-01","metric":"book.rating","v":2,"value":7}
{"date":"2026-07-20","metric":"book.rating","v":2,"value":8}
{"date":"2026-03-15","metric":"book.rating","v":1,"value":5}
```

The last record was added months late. It is still read as 5 out of 5, because it says so itself.

### Completeness {#section-6.3}

> **M-32 · SHOULD · writers** A definition SHOULD say everything needed to read and present its metric within its own version: the kind of number, its unit or bounds, the labels its lines may carry, how values combine, and a plain description.

A reader should not need another version, another file or an application's settings to understand a record.

### Kinds {#section-6.4}

| Kind | The value is | Also requires | Combined by default as |
|---|---|---|---|
| `quantity` | any number, in a unit | `unit`, `combine` | as it states |
| `count` | a whole number, zero or more | | sum |
| `score` | a number between two bounds | `min`, `max` | mean |
| `flag` | 0 or 1 | | sum |
| `event` | no value: it defines a type of event | | |

> **M-33 · MUST · files** A definition of kind `quantity` MUST carry `unit`.

> **M-34 · MUST · files** A definition of kind `score` MUST carry `min` and `max`, with `min` lower than `max`.

### Units {#section-6.5}

> **M-35 · MUST · files** `unit` MUST be one unit code, or a list of unit codes that measure the same thing. A unit code MUST come from the published list of accepted unit codes, which is drawn from UCUM, or be an ISO 4217 currency code.

> **M-36 · SHOULD · readers** When a definition lists several units, a reader SHOULD show totals and charts in the first unit listed.

When a definition states a single unit, every value is in that unit and a record does not repeat it. When a definition lists several, every record states which one it uses.

```jsonl
{"format":"plaintext-metrics/0.2.0","set":"ada/journal"}
{"define":"walk.distance","v":1,"kind":"quantity","unit":["km","m"],"name":"Walking distance","combine":"sum"}
{"at":"2026-11-26T09:00+01:00","metric":"walk.distance","v":1,"value":2.5,"unit":"km"}
{"at":"2026-11-26T13:00+01:00","metric":"walk.distance","v":1,"value":800,"unit":"m"}
```

2.5 km and 800 m add up to 3.3 km: the definition allows both units and names kilometres first.

### Combining values {#section-6.6}

> **M-37 · MUST · files** If present, `combine` MUST be one of `sum`, `mean`, `min`, `max` and `last`.

> **M-78 · MUST · files** A definition of kind `quantity` MUST carry `combine`, because some quantities add up and others average.

> **M-38 · SHOULD · readers** When `combine` is absent, a reader SHOULD use the mean for a score, and the sum for a count or a flag.

> **M-39 · MUST NOT · readers** A reader MUST NOT add together the values of different metrics. `combine` works within one metric.

### Labels {#section-6.7}

A label sorts the lines of one metric into types, such as reading on paper and listening to an audiobook.

> **M-40 · MUST · files** A definition MUST declare each label its lines may carry, in `labels`. Each declaration MUST be a list of allowed values, or the word `text` or `number` for a free value.

> **M-41 · MUST NOT · files** A label MUST NOT have the name of a field of the format.

```jsonl
{"format":"plaintext-metrics/0.2.0","set":"ada/journal"}
{"define":"reading.time","v":1,"kind":"quantity","unit":"min","name":"Reading time","combine":"sum","labels":{"medium":["paper","ebook","audio"]}}
{"at":"2026-11-26T07:30+01:00","until":"2026-11-26T08:05+01:00","metric":"reading.time","v":1,"value":35,"medium":"paper"}
{"at":"2026-11-26T22:10+01:00","until":"2026-11-26T22:40+01:00","metric":"reading.time","v":1,"value":30,"medium":"audio"}
```

Total reading time for the day is still a plain sum, and the label separates the two kinds.

## Record lines {#section-7}

A record states one number, for one metric, at one time.

### Fields {#section-7.1}

| Field | Required | Meaning |
|---|---|---|
| `metric` | yes | The name of the metric. |
| `v` | yes | The version of the definition this record was written against. |
| `value` | yes | The number. |
| `at` | one of `at` and `date` | The moment it happened: date, time and offset from UTC. |
| `date` | one of `at` and `date` | The day, month or year it belongs to. |
| `until` | no | The end of a span that starts at `at`. |
| `unit` | when the definition lists several | Which of the definition's units this value is in. |
| labels | no | Any label the definition declares, written as its own field. |
| `lat`, `lon` | no | Where it happened, in decimal degrees. |
| `note` | no | Short text for people. |
| `of` | no | The `id` of the event this record belongs to. |
| `by` | no | The device, app or person that recorded it. |
| `ref` | no | The identifier of this item in the source named by `by`. |
| `id` | no | An identifier for this line. |
| `meta` | no | An object for anything else. |

> **M-42 · MUST · files** A record MUST carry `metric`, `v` and `value`, and at least one of `at` and `date`.

> **M-43 · MUST · files** `value` MUST be a finite JSON number.

> **M-44 · MUST · files** `value` MUST fit the kind of its definition: within the bounds of a score, a whole number of zero or more for a count, and 0 or 1 for a flag.

### Time {#section-7.2}

A record is about a moment, a calendar period, or a span. The fields that are written say which.

> **M-45 · MUST · files** `at` MUST be a date and a time with an offset from UTC, such as `2026-11-26T08:10+01:00`. Seconds are optional.

> **M-46 · SHOULD · writers** A writer SHOULD use the offset of the place where it happened, not UTC.

> **M-47 · MUST · files** `date` MUST be a day (`2026-11-26`), a month (`2026-11`) or a year (`2026`).

> **M-48 · MUST · files** `until` MUST appear only together with `at`, and MUST NOT be earlier than it.

A month or a year is for a total over that period. The precision that is written is the precision that is meant: a daily total needs no invented time of day, and a run keeps its start and end.

### Which day a record counts toward {#section-7.3}

> **M-49 · MUST · readers** A reader MUST take a record's day from `date` when it is present, and otherwise from the date written in `at`, read as written, with no conversion to another time zone.

A record may carry both. Then `at` says when it happened and `date` says which day it counts toward. There is no file-wide setting for when a day begins. A tool that counts the small hours toward the previous day writes `date` on those records:

```jsonl
{"at":"2026-11-27T00:40+01:00","date":"2026-11-26","metric":"reading.time","v":1,"value":25,"medium":"paper"}
```

### Units on records {#section-7.4}

> **M-50 · SHOULD NOT · writers** A writer SHOULD NOT state `unit` on a record whose definition states a single unit.

> **M-51 · MUST · files** When a definition lists several units, every record of it MUST state `unit`. A `unit` on a record MUST be one that its definition allows.

### Labels on records {#section-7.5}

> **M-52 · MUST · files** A label MUST be written as its own field on the line, as `"medium":"paper"` above.

> **M-53 · SHOULD · files** Every field on a record or an event that is not a field of the format SHOULD be a label that its definition declares.

> **M-54 · MUST · files** A declared label MUST take a value that its declaration allows.

### Place {#section-7.6}

A record or an event may say where it happened. `lat` and `lon` are to place what `at` is to time.

> **M-55 · MUST · files** `lat` and `lon` MUST appear together. `lat` MUST be a number from -90 to 90 and `lon` a number from -180 to 180, in decimal degrees.

> **M-56 · SHOULD · writers** A writer SHOULD keep a dense track, such as a run sampled every second, in its own track file.

```jsonl
{"format":"plaintext-metrics/0.2.0","set":"ben/training"}
{"define":"run","v":1,"kind":"event","name":"Run"}
{"define":"elevation","v":1,"kind":"quantity","unit":"m","combine":"mean"}
{"at":"2026-11-26T07:30+01:00","until":"2026-11-26T08:22+01:00","event":"run","v":1,"lat":41.9028,"lon":12.4964,"id":"run-1126"}
{"at":"2026-11-26T07:41+01:00","metric":"elevation","v":1,"value":52,"lat":41.9109,"lon":12.4818,"of":"run-1126"}
```

### Sources and identity {#section-7.7}

> **M-57 · MUST · files** An `id` MUST be unique within its file.

> **M-58 · SHOULD · files** A pair of `by` and `ref` SHOULD be unique within its file.

> **M-59 · MUST · files** `meta`, if present, MUST be a JSON object.

> **M-60 · MUST NOT · readers** A reader MUST NOT need `meta` to interpret a value.

`by` and `ref` make imports repeatable: an importer writes the source and the item's identifier there, and running the import again finds the same pair and adds nothing. An `id` is only for pointing. A record needs one only when a note or a tool refers to it.

```jsonl
{"format":"plaintext-metrics/0.2.0","set":"ada/journal"}
{"define":"room.temperature","v":1,"kind":"quantity","unit":"Cel","name":"Room temperature","combine":"mean"}
{"define":"books.finished","v":1,"kind":"count","name":"Books finished"}
{"define":"reading.done","v":1,"kind":"flag","about":"1 if any reading happened that day."}
{"at":"2026-11-26T08:10+01:00","metric":"room.temperature","v":1,"value":19.5,"by":"sensor-7","ref":"r-88213"}
{"date":"2026-10","metric":"books.finished","v":1,"value":3}
{"date":"2026-11-26","metric":"reading.done","v":1,"value":1,"note":"Twenty minutes before breakfast"}
```

## Event lines {#section-8}

Some numbers belong together, such as the distance and the average heart rate of one run. An event line stands for the occasion itself. It has a type, a time and an identifier, and no value of its own. Records join it by naming its `id` in `of`.

### Fields {#section-8.1}

| Field | Required | Meaning |
|---|---|---|
| `event` | yes | The name of the event type, defined with kind `event`. |
| `v` | yes | The version of that definition. |
| `id` | yes | The identifier that member lines cite. |
| `at` | one of `at` and `date` | When it happened, with the same rules as a record. |
| `date` | one of `at` and `date` | The day, month or year it belongs to. |
| `until` | no | When it ended. |
| `of` | no | The `id` of a larger event this one is part of. |
| labels, `lat`, `lon`, `note`, `by`, `ref`, `meta` | no | As on a record. |

> **M-61 · MUST · files** An event MUST carry `event`, `v` and `id`, and at least one of `at` and `date`.

> **M-62 · MUST NOT · files** An event MUST NOT carry `value`.

> **M-63 · MUST · files** The definition that an event line cites MUST have the kind `event`, and the definition that a record cites MUST NOT.

```jsonl
{"format":"plaintext-metrics/0.2.0","set":"ada/training"}
{"define":"run","v":1,"kind":"event","name":"Run","metrics":["distance","heart_rate.average"],"labels":{"surface":["road","trail","track"]}}
{"define":"distance","v":1,"kind":"quantity","unit":"km","combine":"sum"}
{"define":"heart_rate.average","v":1,"kind":"quantity","unit":"/min","combine":"mean"}
{"at":"2026-11-26T07:30+01:00","until":"2026-11-26T08:22+01:00","event":"run","v":1,"surface":"trail","note":"River loop","id":"run-1126"}
{"at":"2026-11-26T07:30+01:00","metric":"distance","v":1,"value":10.2,"of":"run-1126"}
{"at":"2026-11-26T07:30+01:00","metric":"heart_rate.average","v":1,"value":148,"of":"run-1126"}
```

The event line holds what is true of the whole run: its type, span, surface and note. The run lasted 52 minutes, which follows from its span and is not stored again.

### Belonging to an event {#section-8.2}

> **M-64 · SHOULD · files** `of` SHOULD name the `id` of an event line in the same file.

> **M-65 · MUST · readers** When `of` names an `id` that no event line has, a reader MUST ignore that `of` and treat the line as standing alone.

> **M-66 · MUST NOT · readers** A reader MUST NOT treat lines as a group merely because they share a value in `of`.

> **M-67 · SHOULD · files** A record in an event SHOULD use a metric that the event's definition lists in `metrics`, and a part SHOULD be of an event type that it lists in `parts`.

A record inside an event still carries its own `at` or `date`, so it can be read without the event line.

### Parts of a larger event {#section-8.3}

An event can be part of another. A triathlon is one event with five parts, and each part has its own records.

```jsonl
{"format":"plaintext-metrics/0.2.0","set":"club/triathlon"}
{"define":"triathlon","v":1,"kind":"event","name":"Triathlon","parts":["swim","ride","run","transition"]}
{"define":"swim","v":1,"kind":"event","metrics":["distance"]}
{"define":"ride","v":1,"kind":"event","metrics":["distance"]}
{"define":"run","v":1,"kind":"event","metrics":["distance"]}
{"define":"transition","v":1,"kind":"event"}
{"define":"distance","v":1,"kind":"quantity","unit":"km","combine":"sum"}
{"at":"2026-09-13T08:00+02:00","until":"2026-09-13T10:41+02:00","event":"triathlon","v":1,"note":"Olympic distance","id":"tri-0913"}
{"at":"2026-09-13T08:00+02:00","until":"2026-09-13T08:31+02:00","event":"swim","v":1,"of":"tri-0913","id":"tri-0913-swim"}
{"at":"2026-09-13T08:00+02:00","metric":"distance","v":1,"value":1.5,"of":"tri-0913-swim"}
{"at":"2026-09-13T08:31+02:00","until":"2026-09-13T08:35+02:00","event":"transition","v":1,"of":"tri-0913","id":"tri-0913-t1"}
{"at":"2026-09-13T08:35+02:00","until":"2026-09-13T09:53+02:00","event":"ride","v":1,"of":"tri-0913","id":"tri-0913-ride"}
{"at":"2026-09-13T08:35+02:00","metric":"distance","v":1,"value":40,"of":"tri-0913-ride"}
{"at":"2026-09-13T09:53+02:00","until":"2026-09-13T09:56+02:00","event":"transition","v":1,"of":"tri-0913","id":"tri-0913-t2"}
{"at":"2026-09-13T09:56+02:00","until":"2026-09-13T10:41+02:00","event":"run","v":1,"of":"tri-0913","id":"tri-0913-run"}
{"at":"2026-09-13T09:56+02:00","metric":"distance","v":1,"value":10,"of":"tri-0913-run"}
```

"Triathlon, 2 hours 41 minutes" is the event line and its span. Nothing is counted twice, because the event has no value to add up.

### A whole and its parts {#section-8.4}

The format has no separate idea of wholes and parts. Three things it already has cover the case:

- **A breakdown is a label.** The warm-up, main part and cool-down of a run are one metric with a `segment` label. The total is the plain sum of its records.
- **The occasion is an event.** The run has a span and no value, so there is no stored total to count twice.
- **Different metrics are never added together.** This is the rule on combining values in section 6.

```jsonl
{"format":"plaintext-metrics/0.2.0","set":"cy/training"}
{"define":"run","v":1,"kind":"event","name":"Run","metrics":["distance"]}
{"define":"distance","v":1,"kind":"quantity","unit":"km","combine":"sum","labels":{"segment":["warmup","main","cooldown"]}}
{"at":"2026-11-26T07:30+01:00","until":"2026-11-26T08:22+01:00","event":"run","v":1,"id":"run-1126"}
{"at":"2026-11-26T07:30+01:00","metric":"distance","v":1,"value":1.5,"segment":"warmup","of":"run-1126"}
```

## Writing and reading {#section-9}

### Writers {#section-9.1}

> **M-68 · SHOULD · writers** A writer SHOULD add new lines at the end of the file.

> **M-69 · MUST · writers** A writer MUST make a correction by replacing exactly one line in place, and a removal by deleting exactly one line.

> **M-70 · MUST NOT · writers** A writer MUST NOT write a line whose purpose is to replace or withdraw another line.

> **M-71 · MUST · writers** A writer MUST leave every other line byte for byte as it was, and in the same order.

> **M-72 · MUST · writers** A writer MUST write back unchanged any field it does not understand.

> **M-73 · SHOULD · writers** A writer SHOULD write each object compactly, with no spaces outside strings.

> **M-74 · SHOULD · writers** A writer SHOULD put the fact first. On a record the order is `at`, `until`, `date`, `metric`, `v`, `value`, `unit`, labels, `lat`, `lon`, `note`, `of`, `by`, `ref`, `id`, `meta`.

### Corrections {#section-9.2}

Fixes are made in place, by a tool that edits. Nothing appended later replaces or withdraws an earlier line, so a file always means exactly what its lines say, and a plain search or sum is never wrong. Version control or the sync system keeps what a line used to say.

```diff
- {"at":"2026-11-26T08:10+01:00","metric":"room.temperature","v":1,"value":91.5}
+ {"at":"2026-11-26T08:10+01:00","metric":"room.temperature","v":1,"value":19.5}
```

### Readers {#section-9.3}

> **M-75 · MUST · readers** A reader MUST accept lines in any order, and the fields of a line in any order.

> **M-76 · MUST · readers** A reader MUST ignore a line that fails a check with an error, leaving it out of every result, and keep reading the rest of the file.

## Checks {#section-10}

Every tool reports problems with the same names, so a person or an agent can act on them. An error means readers ignore the line. A warning means the line is still used.

> **M-77 · MUST · readers** A tool that reports problems MUST use the names in this section.

| Name | Level | Meaning |
|---|---|---|
| `bad_json` | error | The line is not valid JSON, or is not an object. |
| `bad_line` | error | The line has none, or more than one, of `format`, `define`, `metric`, `event`. |
| `missing_field` | error | A required field is absent. |
| `bad_value` | error | A field has the wrong form, such as a `value` that is not a number. |
| `undefined` | error | A record or event cites a name and version that the file does not define. |
| `definition_conflict` | error | Two definitions with the same name and version differ. |
| `out_of_range` | error | A value breaks its kind: outside a score's bounds, not whole for a count, not 0 or 1 for a flag. |
| `unit_mismatch` | error | A record's `unit` is not one its definition allows, or is missing when the definition lists several. |
| `bad_span` | error | `until` is present without `at`, or is earlier than it. |
| `duplicate_id` | error | Two lines share an `id`. |
| `header` | error | The file has no header line, or more than one. |
| `missing_event` | warning | `of` names an `id` that no event line has. Readers ignore that `of`. |
| `duplicate_ref` | warning | Two lines share the same `by` and `ref`. |
| `undeclared_label` | warning | A field is neither a field of the format nor declared by the definition. |

## Open questions {#section-12}

These points are undecided. Rules that depend on them may change.

1. **A file from a newer minor version.** A minor version adds to the format without breaking it. What a reader does with a file whose minor version is newer than the one it knows is not yet stated.
2. **A period total beside the records it totals.** Nothing yet stops one metric from holding both a monthly total and the daily records behind it, which a sum would count twice.
3. **Two records that share an `id`.** This is an error, so readers ignore both lines even though each value is readable. It may become a warning for records.
4. **The list of accepted unit codes.** Rule [[M-35](#M-35)] points at a published list that has not been written yet.
5. **Roles for tools.** What a reader, an appender, an editor and a checker must each do will be a separate document.
