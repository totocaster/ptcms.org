Plaintext Tasks is a task-oriented plain-text format designed for lists that should remain readable without specialized software, patch-friendly for agents, and durable over time.

It follows the Plaintext Commons stance closely: the file is the source of truth, syntax should stay legible in a basic editor, and software should assist the corpus rather than annex it.

## Design goals {#section-1}

- Be readable and writable in any plain-text editor.
- Keep task titles visually clean instead of packing state and metadata into one overloaded line.
- Support sections, subtasks, notes, metadata, and archive workflows without hidden database state.
- Stay deterministic enough that apps can parse and rewrite files reliably.
- Make small, local edits easy for both humans and AI agents.

## Non-goals {#section-2}

- Full Markdown compatibility.
- Rich-text formatting.
- Arbitrary block syntax.
- Hidden task state stored only in an app database.

## Positioning {#section-3}

Plaintext Tasks borrows familiar surface syntax from Markdown, including:

- a single document title line
- headings
- checklist markers
- plain paragraphs
- indentation-based hierarchy

That surface familiarity is intentional, but Plaintext Tasks is not generic Markdown. It is a strict format with task-specific parsing rules.

## File conventions {#section-4}

- Encoding: UTF-8
- Line endings: `LF` preferred, `CRLF` accepted
- Canonical extension: `.tasks.md`

Apps may support additional extensions, but `.tasks.md` is the recommended interchange form.

## Document model {#section-5}

A Plaintext Tasks document has up to two top-level regions:

1. an active region
2. an archive region

The archive region is optional. If present, it begins at a root-level separator line containing exactly:

```
---
```

Everything above the separator is active content. Everything below it is archive or logbook content.

## Line types {#section-7}

Plaintext Tasks v0.1.1 recognizes seven line types:

1. blank line
2. document title line
3. section heading line
4. task line
5. metadata line
6. note line
7. archive separator line

### Blank lines {#section-7.1}

Blank lines contain no visible characters and may appear between blocks for readability.

### Document title line {#section-7.2}

A document title line starts with exactly one `#`, followed by one space, followed by title text.

```
# Workboard
```

Rules:

> **T-1** The document title is optional.

> **T-2 · SHOULD** If present, it should appear at most once.

> **T-3 · SHOULD** If present, it should appear before any sections, tasks, or notes in the active region.

> **T-4** It names the entire list, not a subsection inside it.

### Section heading line {#section-7.3}

A section heading line starts with two to six `#` characters, followed by one space, followed by section text.

```
## Work
### Personal
#### Errands
```

Section headings define section boundaries and nesting. They may contain notes and tasks until the next heading of the same or higher level, or until the archive separator.

### Task line {#section-7.4}

A task line has this shape:

```
- [ ] Task title
```

Valid task states in v0.1.1:

- `[ ]` open
- `[x]` done
- `[>]` deferred
- `[-]` canceled

Examples:

```
- [ ] Ship beta
- [x] File taxes
- [>] Review notes next week
- [-] Cancel old subscription
```

Rules:

> **T-5** Only `-` is valid as the task bullet marker in v0.1.1.

> **T-6 · MUST** The checkbox token must be spaced exactly as shown.

> **T-7** The task title is plain text.

### Metadata line {#section-7.5}

A metadata line belongs to a non-nested task block and has this shape:

```
@key: value
```

Example:

```
- [ ] Ship beta
  @date: 2026-03-28
  @due: 2026-04-01
  @priority: 1
```

Rules:

> **T-8 · SHOULD · writers** Metadata keys are case-insensitive semantically, though writers should preserve original casing when practical.

> **T-9** Metadata values are plain text.

> **T-10 · MUST** Metadata lines must be indented deeper than their parent task line.

> **T-11** Metadata lines are only valid for non-nested tasks in v0.1.1.

> **T-12 · MUST** Unknown metadata keys are valid and must be preserved.

Reserved metadata keys in v0.1.1:

- `@id`
- `@created`
- `@date`
- `@due`
- `@done`
- `@defer-until`
- `@canceled`
- `@priority`

Recommended value forms:

- `@created`, `@date`, `@due`, `@done`, `@defer-until`, `@canceled`: `YYYY-MM-DD`
- `@priority`: `1`, `2`, or `3`
- `@id`: stable opaque identifier string

`@date` marks the day a task becomes relevant in the default active list. It controls visibility timing, not deadline semantics.

### Note line {#section-7.6}

A note line is plain text attached to the nearest heading or task block at the immediately shallower indentation level.

```
- [ ] Ship beta
  Waiting on icons from design.
  Share candidate build with QA once the icons arrive.
```

Rules:

> **T-13** Note lines do not begin with checklist syntax, heading syntax, metadata syntax, or archive separator syntax.

> **T-14 · MUST** Note lines must be indented deeper than their parent heading or task.

> **T-15** Consecutive note lines remain distinct lines.

### Archive separator line {#section-7.7}

The archive separator line must:

> **T-16 · MUST** appear at root indentation

> **T-17 · MUST** contain exactly `---`

> **T-18 · MUST** appear at most once in a document

If no separator exists, the whole document is active content.

## Indentation and hierarchy {#section-8}

Hierarchy is indentation-based.

Canonical write rules:

> **T-19 · writers** One indentation level equals two spaces.

> **T-20 · MUST NOT · writers** Tabs must not be written by canonical serializers.

Read tolerance:

> **T-21 · MAY · readers** Readers may accept tabs or other indentation widths for import.

> **T-22 · SHOULD · writers** Writers should normalize to two-space indentation.

Hierarchy rules:

> **T-23** A child line is indented exactly one level deeper than its parent block in canonical form.

> **T-24** Child tasks are subtasks.

> **T-25** Child notes belong to the nearest heading or task at the immediately shallower indentation level.

> **T-26** Child tasks inherit effective metadata from the nearest ancestor task.

> **T-27** Nested tasks do not define their own metadata in v0.1.1.

Example:

```
## Work

- [ ] Ship beta
  @due: 2026-04-01
  Waiting on icons.
  - [ ] Email QA
```

In that example, `Email QA` is a subtask of `Ship beta` and inherits the parent task's effective due date.

## Metadata inheritance {#section-9}

Metadata inheritance is part of the format semantics.

In v0.1.1:

> **T-28** only non-nested tasks define metadata

> **T-29** nested tasks inherit effective metadata from the nearest ancestor task

> **T-30** nested tasks do not override inherited metadata

Example:

```
- [ ] Ship beta
  @due: 2026-04-01
  - [ ] Email QA
  - [ ] Upload release notes
```

> **T-31 · SHOULD NOT · writers** Canonical writers should not duplicate inherited metadata onto nested tasks.

## State semantics {#section-10}

### Open {#section-10.1}

`[ ]` means the task is active and not completed.

### Done {#section-10.2}

`[x]` means the task is completed.

Recommended companion metadata:

```
@done: YYYY-MM-DD
```

### Deferred {#section-10.3}

`[>]` means the task is intentionally postponed but still relevant.

Recommended companion metadata:

```
@defer-until: YYYY-MM-DD
```

### Canceled {#section-10.4}

`[-]` means the task will not be completed.

Recommended companion metadata:

```
@canceled: YYYY-MM-DD
```

## Archive semantics {#section-11}

Archived content lives below the `---` separator.

Archive rules:

> **T-32** Archived items remain valid Plaintext Tasks content.

> **T-33 · SHOULD · apps** Apps should preserve original task structure, metadata, notes, and subtasks when moving items to the archive.

> **T-34 · MAY · apps** Apps may add archival metadata such as `@done` when archiving, but should not require it for parsing.

> **T-35 · MAY** The archive region may contain headings, notes, and tasks.

Recommended app behavior:

- Incomplete items remain in the active region.
- Completed items may be moved to the archive region manually or by explicit archive commands.
- The default view should show active content only.
- Archive views should behave like a logbook or history.

## Parsing and writing rules {#section-12}

General parser expectations:

> **T-36 · readers** Parse top to bottom.

> **T-37 · readers** Preserve line order.

> **T-38 · readers** Preserve blank lines when practical.

> **T-39 · readers** Preserve unknown metadata keys.

Parent resolution:

> **T-40 · readers** Metadata lines attach to the nearest preceding non-nested task one level up.

> **T-41 · readers** Note lines attach to the nearest preceding heading or task one level up.

> **T-42 · readers** Nested task lines attach to the nearest preceding task one level up.

Canonical writers should:

> **T-43 · SHOULD · writers** emit UTF-8 text

> **T-44 · SHOULD · writers** use two spaces per indentation level

> **T-45 · SHOULD · writers** use exactly one space after `#`, `-`, and metadata colons where applicable

> **T-46 · SHOULD · writers** preserve task titles except for explicit user edits

> **T-47 · SHOULD · writers** emit the archive separator as exactly `---`

> **T-48 · SHOULD · writers** keep the active region above the archive region

> **T-49 · SHOULD · writers** avoid duplicating inherited metadata onto nested tasks

Canonical writers should not:

> **T-50 · SHOULD NOT · writers** silently convert note lines into metadata

> **T-51 · SHOULD NOT · writers** silently move tasks across the archive separator

> **T-52 · SHOULD NOT · writers** rewrite unknown metadata keys into different names

> **T-53 · SHOULD NOT · writers** hide app-only identifiers outside explicit metadata lines

> **T-54 · SHOULD NOT · writers** emit metadata lines for nested tasks

> **T-55 · MAY · readers** Tolerant readers may choose to accept malformed input, but destructive rewrites should be avoided.

## UI mapping {#section-13}

The format is file-first, but it maps cleanly into native task apps:

- document title to list title
- section headings to sections
- task title to the main task row
- metadata to subtext or inspector fields
- inherited metadata shown as inherited, not copied into child task text
- notes to expanded detail text
- subtasks to indented child rows
- archive region to a logbook or archive view

## Compatibility {#section-14}

Plaintext Tasks is designed to be:

- hand-editable in any text editor
- diff-friendly in version control
- patch-friendly for AI agents

It is not intended to be fully interoperable with generic Markdown task parsers, because v0.1.1 includes task-specific semantics such as:

- custom status tokens
- structured metadata lines
- archive-region semantics
- indentation-based task hierarchy
- metadata inheritance for nested tasks

## Out of scope for v0.1.1 {#section-15}

Future versions may standardize topics such as recurrence, richer date-time values, references between tasks, or stricter ID rules. Those are intentionally left out of v0.1.1 to keep the first version small, readable, and durable.
