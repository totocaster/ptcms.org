# Plaintext Tasks v1.0.0

Plaintext Tasks is a task-oriented plain-text format designed for lists that should remain readable without specialized software, patch-friendly for agents, and durable over time.

It follows the Plaintext Commons stance closely: the file is the source of truth, syntax should stay legible in a basic editor, and software should assist the corpus rather than annex it.

## Design goals

- Be readable and writable in any plain-text editor.
- Keep task titles visually clean instead of packing state and metadata into one overloaded line.
- Support sections, subtasks, notes, metadata, and archive workflows without hidden database state.
- Stay deterministic enough that apps can parse and rewrite files reliably.
- Make small, local edits easy for both humans and AI agents.

## Non-goals

- Full Markdown compatibility.
- Rich-text formatting.
- Arbitrary block syntax.
- Hidden task state stored only in an app database.

## Positioning

Plaintext Tasks borrows familiar surface syntax from Markdown, including:

- a single document title line
- headings
- checklist markers
- plain paragraphs
- indentation-based hierarchy

That surface familiarity is intentional, but Plaintext Tasks is not generic Markdown. It is a strict format with task-specific parsing rules.

## File conventions

- Encoding: UTF-8
- Line endings: `LF` preferred, `CRLF` accepted
- Canonical extension: `.tasks.md`

Apps may support additional extensions, but `.tasks.md` is the recommended interchange form.

## Document model

A Plaintext Tasks document has up to two top-level regions:

1. an active region
2. an archive region

The archive region is optional. If present, it begins at a root-level separator line containing exactly:

```
---
```

Everything above the separator is active content. Everything below it is archive or logbook content.

## Quick example

```
# Workboard

## Work

Shared notes for current work items.

- [ ] Ship beta
  @id: 6a7a5b2e
  @created: 2026-03-25
  @due: 2026-04-01
  Waiting on icons from design.
  - [ ] Email QA
  - [ ] Prepare release notes

- [>] Review onboarding copy
  @defer-until: 2026-03-28

## Personal

- [ ] Book dentist
  @due: 2026-03-31

---

## Archive

- [x] File taxes
  @done: 2026-03-20

- [-] Cancel old ISP contract
  @canceled: 2026-03-18
```

## Line types

Plaintext Tasks v1.0.0 recognizes seven line types:

1. blank line
2. document title line
3. section heading line
4. task line
5. metadata line
6. note line
7. archive separator line

### Blank lines

Blank lines contain no visible characters and may appear between blocks for readability.

### Document title line

A document title line starts with exactly one `#`, followed by one space, followed by title text.

```
# Workboard
```

Rules:

- The document title is optional.
- If present, it should appear at most once.
- If present, it should appear before any sections, tasks, or notes in the active region.
- It names the entire list, not a subsection inside it.

### Section heading line

A section heading line starts with two to six `#` characters, followed by one space, followed by section text.

```
## Work
### Personal
#### Errands
```

Section headings define section boundaries and nesting. They may contain notes and tasks until the next heading of the same or higher level, or until the archive separator.

### Task line

A task line has this shape:

```
- [ ] Task title
```

Valid task states in v1.0.0:

- `[ ]` open
- `[x]` done
- `[>]` deferred
- `[-]` canceled

Examples:

```
- [ ] Ship beta
- [x] File taxes
- [>] Review notes next week
- [-] Cancel old subscription
```

Rules:

- Only `-` is valid as the task bullet marker in v1.0.0.
- The checkbox token must be spaced exactly as shown.
- The task title is plain text.

### Metadata line

A metadata line belongs to a non-nested task block and has this shape:

```
@key: value
```

Example:

```
- [ ] Ship beta
  @date: 2026-03-28
  @due: 2026-04-01
  @priority: 1
```

Rules:

- Metadata keys are case-insensitive semantically, though writers should preserve original casing when practical.
- Metadata values are plain text.
- Metadata lines must be indented deeper than their parent task line.
- Metadata lines are only valid for non-nested tasks in v1.0.0.
- Unknown metadata keys are valid and must be preserved.

Reserved metadata keys in v1.0.0:

- `@id`
- `@created`
- `@date`
- `@due`
- `@done`
- `@defer-until`
- `@canceled`
- `@priority`

Recommended value forms:

- `@created`, `@date`, `@due`, `@done`, `@defer-until`, `@canceled`: `YYYY-MM-DD`
- `@priority`: `1`, `2`, or `3`
- `@id`: stable opaque identifier string

`@date` marks the day a task becomes relevant in the default active list. It controls visibility timing, not deadline semantics.

### Note line

A note line is plain text attached to the nearest heading or task block at the immediately shallower indentation level.

```
- [ ] Ship beta
  Waiting on icons from design.
  Share candidate build with QA once the icons arrive.
```

Rules:

- Note lines do not begin with checklist syntax, heading syntax, metadata syntax, or archive separator syntax.
- Note lines must be indented deeper than their parent heading or task.
- Consecutive note lines remain distinct lines.

### Archive separator line

The archive separator line must:

- appear at root indentation
- contain exactly `---`
- appear at most once in a document

If no separator exists, the whole document is active content.

## Indentation and hierarchy

Hierarchy is indentation-based.

Canonical write rules:

- One indentation level equals two spaces.
- Tabs must not be written by canonical serializers.

Read tolerance:

- Readers may accept tabs or other indentation widths for import.
- Writers should normalize to two-space indentation.

Hierarchy rules:

- A child line is indented exactly one level deeper than its parent block in canonical form.
- Child tasks are subtasks.
- Child notes belong to the nearest heading or task at the immediately shallower indentation level.
- Child tasks inherit effective metadata from the nearest ancestor task.
- Nested tasks do not define their own metadata in v1.0.0.

Example:

```
## Work

- [ ] Ship beta
  @due: 2026-04-01
  Waiting on icons.
  - [ ] Email QA
```

In that example, `Email QA` is a subtask of `Ship beta` and inherits the parent task's effective due date.

## Metadata inheritance

Metadata inheritance is part of the format semantics.

In v1.0.0:

- only non-nested tasks define metadata
- nested tasks inherit effective metadata from the nearest ancestor task
- nested tasks do not override inherited metadata

Example:

```
- [ ] Ship beta
  @due: 2026-04-01
  - [ ] Email QA
  - [ ] Upload release notes
```

Canonical writers should not duplicate inherited metadata onto nested tasks.

## State semantics

### Open

`[ ]` means the task is active and not completed.

### Done

`[x]` means the task is completed.

Recommended companion metadata:

```
@done: YYYY-MM-DD
```

### Deferred

`[>]` means the task is intentionally postponed but still relevant.

Recommended companion metadata:

```
@defer-until: YYYY-MM-DD
```

### Canceled

`[-]` means the task will not be completed.

Recommended companion metadata:

```
@canceled: YYYY-MM-DD
```

## Archive semantics

Archived content lives below the `---` separator.

Archive rules:

- Archived items remain valid Plaintext Tasks content.
- Apps should preserve original task structure, metadata, notes, and subtasks when moving items to the archive.
- Apps may add archival metadata such as `@done` when archiving, but should not require it for parsing.
- The archive region may contain headings, notes, and tasks.

Recommended app behavior:

- Incomplete items remain in the active region.
- Completed items may be moved to the archive region manually or by explicit archive commands.
- The default view should show active content only.
- Archive views should behave like a logbook or history.

## Parsing and writing rules

General parser expectations:

- Parse top to bottom.
- Preserve line order.
- Preserve blank lines when practical.
- Preserve unknown metadata keys.

Parent resolution:

- Metadata lines attach to the nearest preceding non-nested task one level up.
- Note lines attach to the nearest preceding heading or task one level up.
- Nested task lines attach to the nearest preceding task one level up.

Canonical writers should:

- emit UTF-8 text
- use two spaces per indentation level
- use exactly one space after `#`, `-`, and metadata colons where applicable
- preserve task titles except for explicit user edits
- emit the archive separator as exactly `---`
- keep the active region above the archive region
- avoid duplicating inherited metadata onto nested tasks

Canonical writers should not:

- silently convert note lines into metadata
- silently move tasks across the archive separator
- rewrite unknown metadata keys into different names
- hide app-only identifiers outside explicit metadata lines
- emit metadata lines for nested tasks

Tolerant readers may choose to accept malformed input, but destructive rewrites should be avoided.

## UI mapping

The format is file-first, but it maps cleanly into native task apps:

- document title to list title
- section headings to sections
- task title to the main task row
- metadata to subtext or inspector fields
- inherited metadata shown as inherited, not copied into child task text
- notes to expanded detail text
- subtasks to indented child rows
- archive region to a logbook or archive view

## Compatibility

Plaintext Tasks is designed to be:

- hand-editable in any text editor
- diff-friendly in version control
- patch-friendly for AI agents

It is not intended to be fully interoperable with generic Markdown task parsers, because v1.0.0 includes task-specific semantics such as:

- custom status tokens
- structured metadata lines
- archive-region semantics
- indentation-based task hierarchy
- metadata inheritance for nested tasks

## Out of scope for v1.0.0

Future versions may standardize topics such as recurrence, richer date-time values, references between tasks, or stricter ID rules. Those are intentionally left out of v1.0.0 to keep the first version small, readable, and durable.
